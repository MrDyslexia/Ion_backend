1Descripción General del Proyecto

1.1 ¿Qué es ALMA?

ALMA (Asistente de Lenguaje para la Memoria y el Aprendizaje) es un sistema de evaluación cognitiva por voz diseñado para administrar el Test 6CIT (Six-item Cognitive Impairment Test) a pacientes de la tercera edad mediante conversación natural en español. Todo el procesamiento de inteligencia artificial corre localmente, sin ninguna dependencia de servicios en la nube.

4.3 Pipeline askLLM()

1. Emitir estado 'thinking'
2. Loop (máx 3 iteraciones):
   a. POST a Ollama /api/chat (streaming)
   b. Parsear JSON line-by-line → emitir deltas al cliente
   c. Si hay tool_call → dispatchToolCall() → continuar
   d. Si hay respuesta texto → verificar looksLikeManualTest()
   e. Salir del loop
3. Persistir mensaje asistente en BD
4. Emitir 'assistant_text_done'
5. ¿Superar umbral compresión? → compressContext() (async)
6. ¿TTS no suprimido? → synthesizeSpeech() (async background)
7. Retornar fullResponse

10Algoritmos de Puntuación

10.1 Puntuación Binaria (year, month)

Año correcto: acepta 2026 | "26" | "veintiséis" | "veinte veintiséis" | "20 26"
  → 0 pts si correcto, 4 pts si incorrecto

Mes correcto: acepta "marzo" | "3" | "tercer mes"
  → 0 pts si correcto, 3 pts si incorrecto

10.2 Puntuación de Hora — ±60 minutos (time)

1. Extraer hora en texto ("las tres y media")
2. Convertir a minutos totales: 3×60 + 30 = 210 min
3. Obtener hora actual del sistema (TZ=America/Santiago)
4. Diferencia mínima sobre ciclo de 12h
5. diff ≤ 60 min → correcto (0 pts) | diff > 60 min → incorrecto (3 pts)

10.3 Puntuación Parcial (countdown, months_reverse)

CalidadCriterioPuntaje
perfect0 errores, secuencia completa0 pts
one_error≤1 error en la secuencia2 pts
failed>1 error o secuencia incompleta4 pts
no_responseSin respuesta4 pts

10.4 Puntuación de Dirección (address_recall)

Dirección: "Manuel Rodríguez 1373 Santiago"
Componentes: [Manuel, Rodríguez, 1373, Santiago]
Por cada componente NO recordado: +2 puntos de error
Rango: 0–10 pts (5 errores × 2 = máximo teórico 10)

Variantes aceptadas para "1373":
  "1373" | "trece setenta y tres" | "mil trescientos setenta y tres"

12.2 Lógica de waitForResponse()

Intento 1 (timeout 40s/60s):
  └─ Esperar respuesta
     ├─ Filler detectado → ignorar, seguir esperando
     ├─ Echo de pregunta → ignorar, seguir esperando
     ├─ Solicitud de repetición → repetir pregunta, re-esperar
     ├─ Intento de cancelación → ir a WAITING_CONFIRM
     ├─ Respuesta válida (ResponseValidator) → DONE
     │    └─ this._lastAcceptedText = normalize(answer.text)  [nuevo v2.1.0]
     ├─ Respuesta inválida → pedir repetición, intento 2
     └─ Timeout → repetir pregunta, intento 2

Intento 2 (timeout 30s):
  └─ Misma lógica
     └─ Timeout → { status: 'no_response' }

WAITING_CONFIRM:
  └─ "¿Desea detener la evaluación?"
     ├─ Sí → throw CancelledError
     └─ No → volver a WAITING_RESPONSE (intento actual)

15.1 — Bug Fix: parseAudioChunk — Alineación de Buffer BUG FIX

Archivo: server.js:666

Problema: En entornos Node.js con pool de buffers compartido, los Buffer recibidos vía Socket.IO pueden tener byteOffset impar. La construcción new Int16Array(raw.buffer, raw.byteOffset, raw.byteLength / 2) lanzaba RangeError: start offset of Int16Array should be a multiple of 2.

Causa raíz: El constructor de TypedArray con (buffer, byteOffset, length) requiere que byteOffset sea múltiplo del tamaño del elemento (2 bytes para Int16). El pool de Node.js puede asignar offsets impares al reutilizar memoria.

// Antes (v2.0.0 — crash):
return new Int16Array(raw.buffer, raw.byteOffset, raw.byteLength / 2);

// Después (v2.1.0 — correcto):
const ab = raw.buffer.slice(raw.byteOffset, raw.byteOffset + raw.byteLength);
return new Int16Array(ab);

El método slice() genera un ArrayBuffer independiente y correctamente alineado.

15.2 — Mejora: Filtrado de Ruido en Buffer Pre-Armado (TestRunner.js) IMPROVEMENT

Archivo: engine/TestRunner.js (+23 líneas)

Problema: STT emitida mientras el TTS reproducía se almacenaba en _bufferedSTT. Al iniciar la siguiente pregunta, ese buffer podía contener interjecciones, el eco de la pregunta recién oída, o la última respuesta aceptada que el micrófono captó.

Solución: Nuevo campo _lastAcceptedText = null y triple verificación en el flush del buffer:

// En _waitSingle() al vaciar _bufferedSTT:
if (isFiller(buffered, 'single'))                         continue; // descarta "uh", "mm"
if (isQuestionEcho(buffered, this._currentQuestion))      continue; // descarta eco pregunta
if (normalize(buffered) === this._lastAcceptedText)        continue; // descarta duplicado

// En waitForResponse() al aceptar una respuesta:
this._lastAcceptedText = normalize(answer.text);

El mismo triple filtro aplica en el flush de _waitVAD().

15.3 — Nueva Función: isConversationNoise() (server.js) NEW FEATURE

Archivo: server.js (~línea 800)

Propósito: Evitar llamadas innecesarias al LLM cuando Vosk transcribe ruido de fondo o produce artefactos en inglés por audio ambiguo.

const ENGLISH_NOISE_RE = /\b(want|try|the|and|with|have|from|they|what|when|where|...)\b/gi;

function isConversationNoise(text) {
  const t = text.trim().toLowerCase();

  // 1. Interjecciones puras (ruido de audio)
  if (/^(e+m+|a+h+|u+h+|hm+|mm+|eh+|ah+|uh+|oh+)\s*$/i.test(t)) return true;

  // 2. ≥2 palabras en inglés en utterance corta (≤7 palabras) = transcripción basura
  const words = t.split(/\s+/);
  if (words.length <= 7) {
    const hits = t.match(ENGLISH_NOISE_RE);
    if (hits && hits.length >= 2) return true;
  }
  return false;
}

Integrado en la rama continue_conversation antes de invocar askLLM().
